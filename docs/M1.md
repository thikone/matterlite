# M1 progress

M1 (MatterLite.md §18): `mm_model`, `mm_api` (login + MFA, bootstrap endpoints), `mm_ws` (auth,
seq, resume, backoff); a CLI test harness prints events.

## Done

- [x] `mm_model`: serde types for the wire format of `server/public/model` — `User`, `Status`,
      `Team`, `TeamMember`, `TeamUnread`, `Channel` (+ `ChannelType`), `ChannelMember`,
      `SidebarCategory`, `Post`, `PostMetadata`, `PostList`, `Reaction`, `FileInfo`, `Emoji`,
      `ThreadResponse`/`ThreadList`, `Preference`, `Role`, `AppError`, `ClientConfig` (flat
      string map with typed accessors and the CRT rule), typed ids (`UserId`, `ChannelId`, ...),
      `SessionToken` (never shown by `Debug`/`Display`). Tolerant everywhere: missing fields
      default, unknown fields are ignored, `null` lists and maps read as empty.
- [x] `mm_model::ws`: frame parsing (events vs responses), `Broadcast`, `ClientAction` frames
      (challenge, ping, typing, presence, active status, statuses) and `WsEvent::decode` for
      about 45 events, with the second JSON parse of string-encoded fields (`post`,
      `channelMember`, `preferences`, `updatedCategories`, ...). Unknown events are
      `WsEvent::Unknown(name)`; a payload missing its entity is a `DecodeError`.
- [x] `mm_api::Client`: `X-Requested-With` + Bearer on every request, no cookies; `AppError`
      bodies (`Unauthorized` for 401), `RateLimited { retry_after }` for 429 (plain-text body,
      `Retry-After` / `X-RateLimit-Reset`), `Status` for non-JSON errors, `Decode`; the server
      version from `X-Version-Id`. `ServerUrl` handles sub-paths, missing schemes and the
      WebSocket URL (`WebsocketURL` override).
      Endpoints: ping, client config/license, login (token from the `Token` header; MFA via
      `ApiError::needs_mfa_code` and a retry with the code), logout, me, preferences, teams, team
      members, team unreads, roles by names, my channels, all channel memberships (NDJSON or
      array), sidebar categories, view channel, channel posts (page/before/after/since, CRT),
      posts around the first unread, users by ids, statuses by ids.
- [x] `mm_ws`: a Tokio task per server with `WsHandle` (send, reconnect now, close) and an
      ordered `WsOutput` stream. Bearer header on the upgrade plus the authentication challenge,
      `seq` checking with 4001 + resume (`connection_id`, `sequence_number`,
      `disconnect_err_code`), `MissedEvents` when the server answers a resume with a new
      connection id, ping every 30 s with 4000 on timeout, the webapp's backoff, graceful close,
      TLS with the OS certificate store (`rustls-platform-verifier`), `ResumeState` to resume
      after an app restart (M2).
- [x] `mm-cli` harness (`cargo run -p mm_cli -- <server-url> <ping|bootstrap|events>`):
      `ping` (version, site URL, sign-in options), `bootstrap` (the WebApp.md §6 startup: teams,
      channels with unread/mention counts under the CRT rule, DM partners and statuses, sidebar
      categories, roles, per-step timings), `events` (connects and prints every event until
      Ctrl+C). `MM_TOKEN`, or a password login with MFA prompt; it logs out sessions it created.
- [x] Tests: 21 `mm_model` unit tests (hand-written fixtures for `null` and unknown fields)
      plus 7 against responses and WebSocket frames captured from the test server
      (`crates/mm_model/fixtures/captured`, `tests/captured.rs`); 12 `mm_api` against
      `wiremock`; 14 `mm_ws` against a scripted tokio-tungstenite server (gap → resume and
      replay, new connection id → missed events, ping timeout, 401, revoked session,
      unconfirmed sessions, backoff, reconnect now).

## Checked against a real server

**Test server** (`docs/MatterLite-TestServer.md`: 12.2.0 from source, seeded, `https://ubuntu`
through nginx and `http://ubuntu:8065`):

| Check | Result |
|---|---|
| `bootstrap --login alice` (password) | Matches the expected starting state (§6 of that document) line for line: 2 teams, 16 channels / 17 memberships, unread and mention counts under CRT, DM partners and statuses, categories |
| MFA (`frank`) | Password only → the code is asked for → login. A wrong code → `api.user.check_user_mfa.bad_code.app_error` |
| Wrong password, deactivated user | `api.user.login.invalid_credentials_email_username`, `api.user.login.inactive.app_error` |
| No teams, no channels (`loner`) | Clean empty state, after handling the 404s below |
| Live events (`events`, `wss://`) | post, edit, reaction add/remove, reply, delete, typing, DM, thread follow/update, channel member update, category update, preferences changed/deleted, all in sequence and decoded |
| Short drop (socket killed on the VM) | Resume with `connection_id` + `sequence_number`; the events posted meanwhile replayed in order; no `hello` |
| 152 events while offline | Still resumed (see below) |
| 300 events while offline | New connection id → `MissedEvents`, `hello`, `seq` from 0 |
| Server restart; 20 s outage | Reset → resume refused → resync; five `502`s from nginx at ~3–5 s each, then reconnect |
| Session revoked | `AuthFailed` at the next ping (≤ 30 s) |

Found on the way (fixed, tested, and documented in WebApp.md):

- **A user in no channel gets 404s, not empty lists**, from `GET /users/me/channels` (with a
  stray `[` before the `AppError`, because the response is streamed) and from
  `channel_members?page=-1`. `mm_api` returns empty lists (WebApp.md §4.4).
- **A revoked session keeps its WebSocket open.** The server stops sending events and answers
  every request with `api.web_socket_router.not_authenticated.app_error`. `mm_ws` now ends with
  `AuthFailed` on that reply (WebApp.md §3.5).
- **`status_change` is sent only to the user whose status changed.** Other users' statuses must
  be polled (`POST /users/status/ids`); WebApp.md said otherwise (§7, §15).
- **Resume holds more than 128 events.** The disconnected connection queues up to 256 more;
  the dead queue of 128 holds frames already sent (WebApp.md §7.4).
- Every preference change also sends a `sidebar_category_updated` without data or team.
- `X-Version-Id` is `version.build.config-hash.licensed`, with an empty build number on
  builds from source: `mm_model::ServerVersion` parses it.

Earlier, against community.mattermost.com (12.2, no account): ping, client config, the
session-expired `AppError` for an invalid token, and `wss://` with the OS certificate store.
That run found that **an invalid token does not fail the WebSocket upgrade**: the server answers
`101` and drops the socket once the challenge fails. `mm_ws` therefore reports
`session_confirmed: false` for connections that end before a ping reply or event, and those
count as failures for the backoff (WebApp.md §7.2).

## Next

M1 is done. Carried into M2 (`docs/M2.md` step 4):

- A full resync on `MissedEvents` and a REST check (`GET /users/me`) after repeated
  unconfirmed disconnects (`session_confirmed: false`), to tell a dead token from a dead
  network.
- Status polling for visible users (`POST /users/status/ids`, ~60 s), since `status_change`
  only covers the user's own status.
- Refetch the client config when the config hash in `X-Version-Id` / `hello` changes.

## Known issues

- Not all events decode yet: `scheduled_post_*`, `channel_bookmark_*`, `draft_*`,
  `post_acknowledgement_*`, `open_dialog` and plugin events are `WsEvent::Unknown` until the
  milestones that need them.
- `mm-cli` is a developer tool: it prints all channels, without paging.
