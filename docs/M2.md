# M2 progress

M2 (MatterLite.md §18): `mm_store` with unread math and timelines; diesel cache with hydration;
sync engine bootstrap and resync; eager sync scheduler P0–P3 + P5 (priority queue, rate limit,
resumable `channel_sync`), FTS for messages; lifecycle (§8.7): hydrate-then-reconcile on
start, persisted WebSocket resume, 1000-post `since` gap handling, outbox with 30 s dedupe
rules, crash-safe cursors, logout dialog that keeps data by default, stored-accounts list.

Everything here is headless (no WarpUI). The UI parts (the logout dialog, the stored-accounts
list on the login screen, sync status) get their data and actions in M2 and their views in M3.

## Steps

1. **`mm_store`** — normalized state, events, unread math, timelines. *Done (below).*
2. **`mm_store` derived views** — *done (below)*. `sidebar(team)` (categories with sorting modes, unread
   filter, DM/GM limit and auto-close rules, WebApp.md §14), `timeline_items(channel)` (date
   separators in the user's timezone, the "new messages" line, combined join/leave posts,
   consecutive-post grouping, join/leave filtering, WebApp.md §9.5).
3. **`mm_cache`** — *done (below)*. diesel 2.3 + bundled SQLite (FTS5 checked), the §8.3 schema as migrations,
   one writer thread with batched transactions (250 ms / 200 rows), hydration into a `Store`,
   `posts_fts`, corruption handling (rename aside, rebuild), `kv` for the WebSocket resume
   state and last team/channel.
4. **`mm_sync` engine** — *done (below)*. The sync thread with its Tokio runtime, `Command`s in and deltas out
   over `async-channel`; startup as §8.2/§8.7: hydrate → `GET /users/me` → P0 bootstrap →
   WebSocket with the persisted `ResumeState`; events → `Store::apply` → deltas + cache
   writes; `Fetch` requests; resync on `MissedEvents` (`since` per channel, 1000-post gap →
   newest page + hole); mark read (`POST /channels/members/me/view`); status polling (~60 s,
   `status_change` covers only my status); refetch the config when the hash in
   `X-Version-Id`/`hello` changes; after repeated unconfirmed disconnects, `GET /users/me` to
   tell a dead token from a dead network.
5. **Eager sync scheduler** — *done (below)*. One priority queue P0–P6 with P0-interactive; token bucket
   (8/s, burst 20), REST concurrency 4, global back-off on `429`; P1 users and emoji, P2
   newest page of every channel in the §8.5 order, P3 followed threads, P5 history backfill
   round-robin within the window; progress in `channel_sync`, resumable after a restart.
6. **Lifecycle** — the outbox (re-send within 30 s with the same `pending_post_id`, otherwise
   reconcile by `since` and show failed), crash-safe cursors (data and cursors in one
   transaction), the `DiagnosticId` check for a reset server, former chats (hidden, kept for
   the retention period), logout that keeps data unless asked, the stored-accounts list and
   per-account delete.
7. **`mm-cli sync`** — runs the engine headless against the test server: first start,
   restart from the cache, offline gap, resend from the outbox. The M2 acceptance check
   before the M3 UI.

    timelines per channel and per thread, followed-thread states and team thread counts,
    preferences, sidebar categories, roles, custom emoji, pending posts, the viewed channel
    and manually-unread channels. Loaders for every bootstrap response and post page.
  - `Store::apply` for every decoded event, with the webapp's rules: counters on `posted`
    (own posts and the viewed channel stay read, muted channels count only mentions,
    join/leave and `silent_notification` posts aren't counted, as the server does), root

    once whichever of the REST reply and the `posted` event comes first, reactions,
    deletes with their replies, read state from other devices, manual unread, membership
    and team changes, preferences (CRT and name-format changes reported), categories (the
    bare update after a preference change ignored), threads, config, license. Missing data
    becomes a `Fetch` request.
  - `Timeline`: loaded posts plus contiguous ranges, joined by the request anchor and the
    server's `prev_post_id`/`next_post_id`; holes between ranges are reported; live posts
    join only a range that reaches the newest post; a `since` reply that hit the 1000-post
    cap doesn't extend the range.
  - Derived views: channel unread (`calculateUnreadCount`), team and DM/GM badges
    (`getTeamsUnreadStatuses`), the name format (preference, server setting, licensed lock)
    and display names, DM/GM channel names, channel permissions from all my roles.
  - Tests: 26 unit tests, and 3 against the captured test-server data. The team badges
    computed from the captured channels and memberships equal the server's
    `/users/me/teams/unread`, and replaying the captured WebSocket frames leaves the expected
    state.

- [x] `mm_cache` (step 3):
  - diesel 2.3 over a bundled SQLite (`libsqlite3-sys` 0.37, FTS5), WAL,
    `synchronous=NORMAL`; the schema as embedded migrations
    (`crates/mm_cache/migrations/`). Entities are JSON blobs of the `mm_model` wire format
    with the columns queries need; timelines and threads keep their `mm_store` ranges.
  - `Cache::open`: creates the directories, checks the file (`PRAGMA quick_check`),
    migrates; a damaged file or a failed migration moves it to
    `cache.sqlite.broken-<unix seconds>` (with `-wal`/`-shm`) and starts empty
    (`OpenReport`). `account_id(server_url, user)` names the per-account directory.
  - `Cache::hydrate` rebuilds a `Store` before any network call: everything but statuses
    and pending posts. Channels without a membership stay in the file (former chats, step
    6) but not in the store.
  - `snapshot_ops(store)` saves a whole store; `ops_for(store, deltas)` turns each change
    into writes carrying copies of the changed entities. The `Writer` thread commits them in
    batches (250 ms or 200 ops), one transaction per batch; `flush` waits for a commit.
    `open_reader` gives a second connection for reads during the session.
  - Message search (`posts_fts`): message text plus message-attachment text and file names,
    `unicode61` with diacritics folded, every word required and the last as a prefix,
    best match then newest, optionally per channel. Explicit deletions leave the index.
  - Tests: 2 unit, 7 integration against the captured data: a snapshot hydrates to the
    same store view (entities, badges, sidebar, timeline items, ranges, threads), and so do
    the captured live events after going through the writer; search; a reader beside the
    writer; a broken file moved aside. 20 000 posts (release build): written with their
    index in 2.3 s, hydrated in 0.1 s, a channel search in 32 ms, 18.8 MB on disk.

- [x] `mm_sync` (step 4):
  - `start(EngineConfig)` runs the engine on its own thread with a Tokio runtime; the UI
    sends `Command`s (open/close channel, focus, load older/newer, open thread, send/retry/
    discard post, shutdown) and receives `Event`s (hydrated, ready, resynced, changes,
    channel opened with its `last_viewed_at`, connection state, logged out, server changed,
    cache moved aside, errors). The store is shared as `Arc<RwLock<Store>>`, the simpler of
    the two options in MatterLite.md §6.2; the engine holds the write lock only for one
    change at a time and never across an await.
  - Startup: hydrate when the account is known → `GET /users/me` (401: logged out, data
    kept; unreachable: retried with backoff while the hydrated store is shown) → resume the
    saved WebSocket session; a lossless resume (`WsOutput::Confirmed { resumed: true }`)
    needs no bootstrap, otherwise P0 bootstrap into the existing store (cached posts and
    timelines stay) and a `since` catch-up of the loaded timelines from the saved
    `synced_through`, with the 1000-post cap turning into the newest page and a hole.
  - Events received during a bootstrap or resync are dropped: the fetched data contains
    them, and applying them on top would count new posts twice; a second, short catch-up
    covers the posts among them.
  - Runtime: events → `Store::apply` → cache writes and `Changed`; `Fetch` requests (a
    channel and my membership, plus the DM partner; teams, categories and roles through a
    full bootstrap); posts by unknown authors fetch their profiles; a post in the viewed
    channel marks it read on the server; `MissedEvents` reruns the bootstrap and catch-up;
    status polling every 60 s (DM partners and the open channel's authors); the client
    config is refetched when the config hash (`X-Version-Id`, `hello`) changes; three
    unconfirmed connections in a row check the token over REST. Unread DMs/GMs get their
    `direct_channel_show`/`group_channel_show` preference, as the webapp does.
  - Channels: opening one loads the unread window or the newest page, reports the old
    `last_viewed_at` and marks it read (only while focused, and not when marked unread by
    hand); older and newer pages; threads. Sending: a pending post at once, `POST /posts` in
    the background, then the server's copy or a failed post with retry/discard.
  - The resume state saved (every 30 s, at disconnects and at shutdown) uses the `seq` of the
    last event the engine **applied**, not the last one `mm_ws` received, so a restart never
    skips events that were queued but not yet applied.
  - `mm_ws`: `WsOutput::Confirmed { resumed }` once per connection, and
    `WsHandle::resume_state()`. `mm_api`: single channel/team and my memberships, create post,
    save preferences, followed threads, post thread.
  - `mm-cli sync --data <dir>`: the engine headless, with commands on stdin.
  - Tests: 5 engine tests against a mock server answering with the captured test-server
    responses (first start fills the cache, a known account draws from the cache first,
    opening a channel loads the unread window and marks it read, a sent post replaces its
    pending copy, an expired token logs out); 1 more `mm_ws` test for `Confirmed`.
  - Checked on the test server (`mm-cli sync` as alice): bootstrap in 70 ms with the
    expected badges; opening `#dev` (unread window, new-messages line, marked read: 32 → 24
    unread); sending; local search; a restart resumes the saved session in 20 ms and replays
    exactly the posts made while it was stopped; a server restart mid-session resyncs and
    catches up on the posts made during the restart.

- [x] Eager sync scheduler (step 5):
  - Every fetch is a job in one queue: interactive (opening a channel, older/newer pages,
    threads, missing profiles), P1 people (`GET /users/known` → `POST /users/ids` in batches
    of 100, `POST /users/ids?since=` for changed profiles, all custom emoji in pages of 200),
    P2 the newest page of each channel, P3 followed threads per team (pages of 25) and the
    replies of those active within the window, P5 backfill in pages of 200, and a `since`
    sweep of loaded channels every 30 minutes (and after a resync) for edits and deletes in
    quiet channels. FIFO within a class, no duplicates among queued and running jobs.
  - Channels are taken in the §8.5 order: mentions, unread, favourites, DMs/GMs, recently
    viewed, the rest. Backfill pages go to the back of the queue, so channels take turns.
  - Jobs only fetch; their results come back to the engine loop, which stays the only
    writer of the store, so live events never wait for a page load (the step 4 limitation).
  - Up to 4 jobs at once; every request (jobs, bootstrap, catch-up, read marks) takes a token
    from one bucket (8/s, burst 20; gentle 4/s and fast presets); a `429` pauses all
    requests for `Retry-After` (10 s without one) and retries the job first. 4xx errors drop
    the job; other errors retry it up to 3 times; interactive failures are reported.
  - Settings (`SyncSettings`): rate, concurrency, history window (off, N days (default 180),
    all), people on/off, sweep interval. Commands `PauseSync` (interactive jobs still run),
    `ResumeSync`, `SyncNow`; `Event::Sync(SyncStatus)` with queued, running, done and the
    number of channels still backfilling, at most every 500 ms and when the sync goes idle.
  - Resumable: backfill progress is the cached timeline ranges themselves, so a restart
    continues where it stopped; the profile refresh time is kept in `kv`.
  - Tests: 5 scheduler unit tests (channel order, P2 selection, backfill window and start,
    threads to load, the queue), 3 limiter tests (burst and rate, the 429 pause, no limit), and
    an engine test where a `429 Retry-After: 1` delays a page by a second and the retry
    succeeds.
  - Checked on the test server, empty cache: 25 jobs in 1.4 s, all 16 channels' newest
    pages, 17 profiles, emoji, the followed thread and `#history` backfilled to its first post
    (600 posts, three pages of 200); local search covers it. A restart hydrates 721 posts,
    resumes, and finds nothing to backfill (5 small jobs).

## Known issues

- Post writes run four statements each (upsert, rowid, index delete and insert) without
  prepared-statement caching for the raw SQL: about 8 600 posts/s, well above what the
  scheduler fetches (8 requests/s × 200 posts), but there's room if backfill needs it.
- The schema has no `files`, `file_text_fts` or `outbox` tables yet: the outbox comes with
  step 6, the attachment tables with M5, each as a new migration.

- Names sort case-insensitively with numeric runs, not by full locale collation (the
  webapp's `localeCompare` with the user's locale).

- `PostEdited` keeps reply data the event lacks, but nothing else; a later `since` sync
  corrects any drift.
- Thread counts for DM/GM threads (no team) aren't tracked yet.
- Avatars (P1 in §8.5) and P4 attachments wait for the image work in M3/M5; P6 extras (pinned
  posts, bookmarks, flagged posts, channel stats) for the milestones that show them.
- The `channel_sync` table is unused: backfill progress is read from the cached timeline
  ranges, which can't disagree with the data. It stays for per-channel sweep times if the
  global sweep turns out too coarse.
- `Fetch::Team`, `Fetch::Categories` and `Fetch::Roles` rerun the whole bootstrap; fine for
  rare events, wasteful if a server sends them often.
- Pending posts live only in memory until the outbox (step 6).
