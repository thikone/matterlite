# M3 progress

M3 (MatterLite.md §18), the MVP: login; Warp-style layout with chat tabs (focus-or-open, LRU
cap, pin, persisted), the tool panel's **Chats** tab (team switcher + categories), the
**Channel** tab (Info, Members, Pinned) and the **History** pane (date groups, local search,
navigate, filter-the-chat); the channel view with paging, Markdown + emoji + code
highlighting, the composer with send/pending/retry, mark read, unread badges, typing
indicator, DMs/GMs, channel switcher, reconnect banner, portable packaging; themes: all Warp
themes + 5 Mattermost themes + `ChatColors`, theme chooser, follow the server theme.

The views live in a new crate, `ml_chat` (chat models and views on top of `mm_sync` and the
`ml_workspace` shell); `matterlite` stays the thin binary. `mm_render` and `mm_emoji` are
headless, like the `mm_*` crates.

## Steps

1. **Session and login** — *done (below)*. `ml_chat::Session`, a singleton model that owns the
   `mm_sync::EngineHandle` and forwards its events on the UI thread; `mm_sync::Auth` for the
   requests made before an engine exists (ping, client config, login) on its own Tokio
   runtime; the token in secure storage (`token:<account id>`, DPAPI file on Windows,
   Secret Service on Linux, Keychain on macOS), never logged. `LoginView`: server URL → ping
   and the server's sign-in options → login id and password → MFA code when asked; the
   stored-accounts list to continue an account (with its size, last use and Delete). On start
   the most recent account with a stored token opens straight into the workspace from its
   cache. A revoked or expired session returns to the login with the account filled in. The
   logout dialog keeps the local data by default (Delete lists the unsent posts); the
   server-reset dialog (archive and start fresh, or keep). The window's root switches between
   login and workspace.
2. **Themes** — `ChatColors` (an optional `chat` section in theme YAML, otherwise
   `ChatColors::derive`), the five Mattermost themes with GitHub-light and Monokai ANSI
   palettes, Mattermost Denim as the default with Quartz/Onyx for system light/dark,
   `from_mattermost_json`, and the **Theme source** setting (Mattermost account by default,
   following the `theme` preferences live and per team; or Local).
3. **Chats tab** — team switcher (dropdown with unread dots and mention counts), filter
   field, the categories from `Store::sidebar` (collapse state saved to the server as the
   webapp does), unread and mention badges, DM status dots, GM member counts, the Unreads
   group, `Alt+↑/↓` and `Alt+Shift+↑/↓`; the engine sends the DM/GM show preferences.
4. **Chat tabs and switcher** — tabs hold chats: focus-or-open, LRU cap (setting, default
   12), pin, close and reopen, labels with the channel icon, name, unread dot or mention
   count; open tabs persisted per account in `kv` and restored; last team and channel;
   `Ctrl/Cmd+K` switcher over every chat with `fuzzy_match` (opens or focuses a tab).
5. **`mm_render` and `mm_emoji`** (headless) — comrak GFM → `MessageDoc` (no raw HTML,
   allowed autolink schemes, image size syntax); mentions, `~channels`
   (`props.channel_mentions`), `:emoji:` and emoticons, hashtags, my mention keys
   highlighted; fenced code highlighted with `syntax_tree` in the theme's ANSI colours;
   emoji-only messages large; system message texts from `type` + `props` (WebApp §12) with
   the `message` fallback; the emoji index generated from `emoji-datasource` and a PNG set
   whose licence allows redistribution.
6. **Channel view** — header (name, header text, member count), the timeline in WarpUI's
   viewported list anchored at the bottom, items from `Store::timeline_items` (full or
   compact post, date separator, new-messages line, combined activity, hole with "load",
   pending and failed posts with Retry/Delete); older pages when scrolled near the top with
   a stable anchor, "Jump to newest"; avatars (disk cache keyed by `last_picture_update`);
   mark read on view and `Esc`; laid-out posts cached by post, `update_at`, width and theme.
7. **Composer** — `ml_editor::EditorView` multi-line with autogrow: Enter sends,
   Shift+Enter newline (Ctrl/Cmd+Enter with `send_on_ctrl_enter`), Enter inside an open
   code block adds a line; `MaxPostSize`; disabled in read-only and archived channels;
   drafts per channel saved to SQLite and restored; typing events sent at most every 5 s and
   shown ("carol is typing…") under the timeline and in the tab label.
8. **Channel tab and History pane** — Channel › Info (header, purpose, favourite, mute, copy
   link, leave), Members (with status), Pinned; History: date groups (Today and Yesterday
   expanded, state in `kv`), one row per message with a plain-text excerpt and icons, local
   search through the shared search bar (FTS5 for plain queries, regex and case-sensitive
   scans), navigate (scroll the chat and flash the post), filter-the-chat with its banner,
   the covered range in the footer.
9. **Connection, packaging, acceptance** — reconnect banner and sync status (pause/resume),
   errors shown instead of only logged; `script/build-portable.{ps1,sh}` and versioned
   archives from CI; the M3 acceptance pass against the test server.

## Done

- [x] Session and login (step 1):
  - `mm_sync::Auth`: the server check (`/system/ping` and the unauthenticated client config:
    site name, version, sign-in methods; `https://` first, then `http://` for a URL typed
    without a scheme) and the login, on a one-thread Tokio runtime whose futures the UI awaits.
    Errors are worded for people (wrong login or password, deactivated, MFA code wrong or
    missing, MFA not set up, account locked after too many attempts, rate limited, the root
    cause of a connection failure).
  - `ml_chat::Session` (singleton model): starts the engine and forwards its events on the UI
    thread (`spawn_stream_local`), ignoring events of an engine it already replaced; keeps the
    connection and sync state; stores the token in secure storage as `token-<account id>` (no
    `:`, since on Windows the key is part of a file name) and removes it when the engine reports
    `LoggedOut`. A logout the user didn't ask for (expired or revoked) returns to the login
    with the server and login filled in and a notice. At launch the most recently used account
    with a stored token opens from its cache; at quit the engine is shut down (state saved,
    cache flushed).
  - `LoginView`: server URL → Continue → login (placeholder worded as the webapp's
    `getInputPlaceholder`) and password → MFA code when the server asks; Enter submits, Tab
    switches fields, Esc goes back; the password is cleared after a wrong one. SSO-only
    servers are told SSO comes later. "On this computer": the stored accounts with size, last
    use and unsent posts; a click opens one (or asks for the password when no login is
    saved), Delete… asks first and removes the data and the saved login.
  - `RootView`: the login while signed out, a fresh `Workspace` per sign-in. The account button
    (initials and a connection dot) at the right end of the tab bar opens the Account dialog:
    user, connection, local data size, **Log out** (keeps the data) and **Log out and delete
    local data**. The server-reset question (start fresh or keep the local copy) and one-time
    notices (a damaged cache moved aside, a token that couldn't be saved) are dialogs too.
    Until the chat views exist, the chat area shows the account, counts and sync state.
  - Binary: secure storage registered per platform (DPAPI files in `state/secure/` on
    Windows, Keychain, Secret Service), and closing the window now quits the app.
  - Tests: the server check and login wording against a mock server (6); the session with a
    real engine and an in-memory secure store: an expired token returns to the login with the
    account filled in and the token removed.
  - Checked by hand on Windows against the test server (portable mode): unknown host, wrong
    password, alice's login, restart straight into the account (WebSocket session resumed),
    logout keeping the data, login again from the stored account (cache hydrated first),
    frank's MFA login with a wrong and a right code, logout with delete, Delete… on the
    login screen.

## Known issues

- Keystrokes injected with `PostMessage` don't reach winit reliably (`WM_CHAR` alone is
  ignored, `WM_KEYDOWN` without the real keyboard state loses letters); scripted UI checks on
  Windows use `SendInput` with the window in front.
